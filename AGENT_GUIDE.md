# KnightNotes — Agent Guide

Orientation for a fresh AI coding session (or new human contributor).
KnightNotes is an interactive chess textbook — **"Chess, explained move by
move."** — a local-first Vue 3 SPA with no server, deployed to GitHub Pages.

## Where authority lives

| Concern | Authoritative source |
|---|---|
| Product intent, scope, domain model, deferred features | [`DESIGN_SPEC.md`](DESIGN_SPEC.md) |
| Architecture map, run/deploy instructions, licensing | [`README.md`](README.md) |
| Current behavior | the source code and its tests (`src/**`, specs in `__tests__/`) — tests are the most precise behavioral record |
| Study content authoring | [`CONTENT_AUTHORING.md`](CONTENT_AUTHORING.md) — the only document content authors need |

**When documentation and implementation disagree:** don't blindly overwrite
either. Read the implementation and its tests, check `git log` for the change
that introduced the difference, and decide whether the doc is stale (update
the doc) or the code drifted from a deliberate contract (fix the code,
test-first). Tests + git history are the tiebreakers.

## Workflow: content-only changes (new game/opening/trap/tactic/endgame)

1. Read `CONTENT_AUTHORING.md` in full.
2. Inspect a nearby existing study in `src/content/<category>/` as a live example.
3. Write/modify the StudySeed JSON (filename = `id`). Never author canonical
   Study JSON, FENs, or node ids by hand — the pipeline generates them.
4. Validate: `npm run validate:content` (schema + chess legality + quality gate).
5. Run `npm test`; run `npm run build` if you changed anything beyond content.
6. Do not touch application code for content work unless the content genuinely
   requires a format change — and then document it in `CONTENT_AUTHORING.md`.

## Workflow: application changes

1. Read `README.md`, then the relevant sections of `DESIGN_SPEC.md`.
2. Inspect the current implementation and its tests before planning.
3. Preserve the layer boundaries: presentation → application → domain →
   infrastructure. Presentation never imports chess.js, idb, or repository
   implementations; the domain layer has zero runtime dependencies.
4. Work test-first; add or update tests with every behavior change.
5. Validate: `npm test`, then `npm run build` (includes the TypeScript check).
6. If public behavior, architecture, or the content contract changed, update
   the matching document (see table above). Deploys are automatic on push to
   `main` and are gated by the full test suite.

## Principles

1. Educational product first: explain **why a move matters**, never narrate
   what visibly moved. Quality of explanation resolves ambiguous decisions.
2. `Study` (in `src/domain/study/types.ts`) is the single canonical runtime
   model. StudySeed and PGN are authoring/interchange formats that compile
   into it — never competing models.
3. All mechanical structure (FENs, ids, plies, parent/child links) is
   generated by replaying moves through the rules engine; hand-written
   position data is a bug.
4. Validate everything: schema, chess legality, and content quality gates run
   in `npm test` and gate every deploy. Legal-but-wrong chess is the failure
   mode validators can't catch — verify scores and endgame technique against
   sources.
5. Prefer a few high-quality studies over many shallow ones.
6. Keep the basic reading experience simple: open study → Next → Next.
   Advanced capability must not complicate that loop.
7. The spec's "Deferred features" list (Stockfish, manual moves, Learn/Test
   modes, accounts, sync…) is deliberate V2 scope — don't introduce it as a
   side effect of unrelated work.
8. No GPL dependencies (keeps future commercialization open).
