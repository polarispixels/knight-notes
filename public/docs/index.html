♞ KnightNotes Documentation

Chess, explained move by move.

KnightNotes is an interactive chess textbook: a browser-based study application where a student steps through famous games, openings, gambits, traps, tactics, endgames, patterns, and variations move by move, with educational commentary at the moments that matter. The product's standard is explaining why an important move matters — not merely showing what moved. It is a local-first single-page app (Vue 3 + TypeScript): no server, no accounts; imported games live in the reader's browser.

This page is the canonical starting point for humans and AI agents working on KnightNotes. Agents: read AGENT_GUIDE.md first — it maps which document is authoritative for which concern, gives task workflows, and states the project's principles.

Start here, by task

Adding or modifying study content

Read CONTENT_AUTHORING.md — the authoritative specification for bundled study content of every kind (famous games, openings, gambits, traps, tactics, endgames, patterns, variations). Authors write StudySeed JSON — moves as SAN plus structured annotations — which the application compiles into its canonical Study representation, generating FENs, node ids, and move relationships automatically. It includes the full field reference, the validation model, the writing-voice guide, and a complete shipped study as a worked example. Content work needs no other document.

Adding or reorganizing openings

Opening lessons are governed by the Opening Catalog (src/data/openings-catalog.json) — the curated taxonomy of opening families, variations, aliases, editorial tiers, and transpositions that powers the openings browser. The "The Opening Catalog" section of CONTENT_AUTHORING.md gives the add-a-new-opening procedure; the ontology and design rationale live in DESIGN_SPEC.md.

Format authority in one sentence

Study is the canonical runtime/domain model; StudySeed is the authoring format for bundled content; PGN is the import/interchange format for user games. The latter two always compile into the former, and generated structure (FENs, ids, relationships) is never written by hand.

Validating work

From the repository root (all three must pass before work is complete; pushes to main deploy automatically, gated by the test suite):

npm run validate:content   # content only: schema + chess legality + quality gate
npm test                   # full suite (domain, PGN, persistence, UI, content)
npm run build              # TypeScript check + production build
